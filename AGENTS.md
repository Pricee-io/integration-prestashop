# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project

Pricee.io PrestaShop plugin (`pricee/`): syncs PrestaShop products to the Pricee.io platform. PHP 7.4+, PrestaShop 1.7.8+.

- `pricee/pricee.php` — main module class (configuration, category listing)
- `pricee/src/Controller/Admin/SyncController.php` — AJAX sync endpoint
- `pricee/src/Service/SyncService.php` — sync logic and Pricee.io API calls
- `pricee/views/templates/admin/` — Smarty admin templates (French labels)
- `pricee/src/Webhook/WebhookService.php` — webhook checks and price-writing rules (`pricee/controllers/front/webhook.php` only reads the request and answers)
- `docs/behavior.md` — what the module does, in plain language (settings, sync, webhook price-writing rules). Keep it in sync with any behavior change. It lives outside `pricee/`, so it is not shipped in the release zip.

## Development

All tooling runs through the Docker dev environment (see `Makefile`):

- `make dev` — shell into the dev container
- `make lint` — php-cs-fixer (fix), `make lint_ci` — dry-run check
- `make analyze` — phpstan
- `make rector` — rector
- `make package` — regenerate `pricee.zip` for release

Run lint and analysis before committing.

## Versioning

The plugin follows [Semantic Versioning](https://semver.org/). The version is defined in three places and all must be updated together:

1. `$this->version` in `pricee/pricee.php`
2. A new `## [x.y.z] - YYYY-MM-DD` entry at the top of `CHANGELOG.md`
3. `<version>` in `pricee/config.xml` (stays in sync with the module version; regenerated by PrestaShop on install)

Bump rules:

- **Patch** (`1.1.0` → `1.1.1`): bug fixes, no behavior change
- **Minor** (`1.1.0` → `1.2.0`): new features or backward-compatible behavior changes
- **Major** (`1.1.0` → `2.0.0`): breaking changes (PrestaShop compatibility drops, config/DB schema changes)

Make the version bump its own commit, titled `Bump version to x.y.z`, separate from feature commits.

Changelog rules (this is a PrestaShop module, so the changelog is read by merchants, not developers):

- Only user-facing changes: what the module user sees or experiences in the back office or front office. Skip CI, tooling, Dependabot, static analysis and internal refactors.
- One short line per change, no implementation details (no function names, no file paths, no "fix X by doing Y" narration).

## Webhook contract

The price-update webhook is received by `pricee/controllers/front/webhook.php` (module front controller `webhook`). The payload is a JSON array of entries signed with HMAC-SHA256 over the **raw request body** using the webhook secret (`X-Signature` header). Each entry carries `url`, `extId` (optional: the shop's internal product ID, null for products synced before external IDs existed), `priceAmount` (the price to set), `priceCurrency`, `currentPriceAmount` (the price Pricee last read on the page: the entry is skipped when the shop's price differs), `timestamp` and `nonce`; entries with a missing/stale timestamp or an already-used nonce are rejected (replay protection). Products are matched by `extId` when present (an unknown `extId` is skipped, never retried by URL), otherwise by the product URL, whose rewrite must be the product's own. `priceAmount` and `currentPriceAmount` are prices as visitors see them on the product page: it must be in the shop default currency (other or missing currencies are skipped) and is converted to tax-excluded before being stored when the shop displays prices tax-included.

Any change to this format is a cross-repo contract: the sender lives in `../app/src/Service/WebhookService.php` and the WooCommerce/Sylius integrations validate the same signature, keep changes backward compatible or coordinate all of them.

## Price-writing rules

Writing a price is the critical action of the module: when in doubt, skip the entry and log why, never guess. The rules (checked in `pricee/src/Webhook/WebhookService.php`) are listed in `docs/behavior.md`, "Price-writing rules": only the base price of a simple, visible product is ever written, and products with any promotion, quantity discount, catalog price rule, ecotax or visitor group discount, whose price changed since Pricee read it, or whose new price would be below cost, are skipped. Promotions are never created or edited. Any change to these rules updates that doc and the tests in `tests/Integration/Webhook/`.

## Tests

`make test` runs the PHPUnit integration tests inside the PrestaShop container (`make start` first). They use PrestaShop's test mode, on `test_prestashop`, a copy of the dev database rebuilt at each run by `tests/prepare-test-db.sh`, and each test is rolled back. A test that triggers an implicit commit (e.g. a module hook running `TRUNCATE`) fails instead of leaking data.

The compatibility CI (`.github/workflows/ps-compat.yml`) also runs them on every supported PrestaShop version (1.7.8, 8.2, 9.2), with a standalone PHPUnit matching each image's PHP (9.6 on PHP 7.4/8.1). Tests must stay compatible with PHP 7.4 and PHPUnit 9.6, and use PrestaShop APIs available in 1.7.8 (or fall back, as `IntegrationTestCase::resetCaches()` does). PrestaShop 1.7.8 cannot switch multistore during a run, so that job runs the suite once single-shop and once multistore (`MULTISTORE=0|1` for `tests/prepare-test-db.sh`); tests needing the other mode are skipped by `setMultistore()`.

## End-to-end tests

`make e2e` (`e2e/run.sh`) starts its own throwaway database and shop containers (never the dev ones) and tests the upgrade from the last release, real HTTP webhook calls and a back-office sync in a browser against a fake Pricee API. `.github/workflows/e2e.yml` runs it on 1.7.8, 8.2 and 9.2. Keep `e2e/shop.php` and `e2e/fake-api.php` compatible with PHP 7.4. When releasing, point `E2E_FROM_REF` in `e2e/run.sh` to the new release commit.

## Multi-shop (multistore)

The module must work correctly on PrestaShop multistore installs:

- Use the shop's own front URL (`Link::getBaseLink($idShop)`) as the website URL when syncing, never the back-office request host: each shop can have its own domain.
- Scope every shop-dependent value explicitly: `Configuration::get`/`updateValue` with `$idShop`, product queries through the `product_shop` join (`SyncService::shopProductsSql`, whose `ps.active` is the shop's flag), products loaded with `new Product($id, false, $idLang, $idShop)`, product links via `getProductLink(..., $idShop)`, categories through `category_shop` and the shop's own home category.
- A sync targets exactly one shop, chosen in a dropdown in the module page (shops of the current back-office context, current shop preselected). Never silently sync a shop other than the selected one.
- On uninstall, `Configuration::deleteByName` already removes the key for every shop and shop group.
- Settings levels (`pricee/src/Settings/SettingsService.php`): Pricee credentials are shared (all shops or group) by default with an optional per-shop value; webhook settings are per shop only and not editable for all shops or a group.
- Webhook price updates must stay within the receiving shop: skip products not associated with the current shop and write the price for that shop only.
